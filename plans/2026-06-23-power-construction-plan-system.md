# 电力配电行业施工方案报告自动生成系统 — 方案规划

## 一、需求概述

**输入** → **处理** → **输出**

```
现场勘察单（文本/图片/表格）
      ↓
   + 施工方案模板（文档）
   + 处置方案知识库（按场景分类）
   + 标准表格库（格式规范）
      ↓
施工方案报告（.docx 格式，行业标准）
```

### 输入形态（现场勘察单）

| 来源 | 可能格式 | 内容举例 |
|------|----------|----------|
| 现场拍照 | 图片 | 杆塔照片、设备铭牌、现场环境 |
| 手写记录 | 图片/PDF | 勘察人员手写备注 |
| 电子表格 | Excel/csv | 设备清单、参数表 |
| 文本描述 | 文字 | 勘察结论、现场情况说明 |

### 输出要求（施工方案报告）

- 格式：Word（.docx）— 行业交付标准
- 内容结构：工程概况 → 施工方案 → 安全措施 → 质量标准 → 进度计划 → 附件
- 样式：统一字体、标题层级、页眉页脚、表格样式
- 引用：引用标准规范编号正确

## 二、架构抉择：三条技术路线

### 路线 A：Dify 工作流（推荐）

**核心架构：**

```
用户上传勘察单 → Dify 工作流入口
    ├─ [多模态 LLM 节点] 图片/PDF → 结构化文本
    ├─ [知识库检索节点]  匹配模板 + 处置方案
    ├─ [LLM 节点]        填充模板 + 生成正文
    ├─ [Code 节点]       python-docx 生成 .docx
    └─ [End 节点]        返回文件下载链接
```

**优势：**
- 多模态识别一步到位（勘察照片→结构化数据）
- 内置知识库（RAG），不用自建检索
- 可视化编排，业务人员可调提示词
- 支持文件上传/下载
- 已有相关案例参考（变压器自动填报系统）

**劣势：**
- Code 节点有执行超时限制（复杂 docx 生成需分段）
- .docx 样式控制不如原生 Python 灵活
- 如果需要对接飞书/企业微信，需要额外配置

**关键技术验证：**
| 验证项 | 预期结论 |
|--------|----------|
| Dify 多模态识别勘察照片 | ✅ Qwen2.5-VL 可行 |
| Dify 知识库检索模板/方案 | ✅ RAG 匹配 |
| Dify Code 节点 python-docx | ⚠️ 需控制代码复杂度，分段生成 |
| .docx 格式兼容性 | ✅ 支持 |

### 路线 B：Hermes Agent Skill（次推荐）

**核心架构：**

```
用户飞书消息发送勘察单 → 调用 Hermes Skill
    ├─ image_analyze / vision_analyze 识别图片
    ├─ 本地知识库（kb-retriever）匹配模板
    ├─ LLM 调用生成报告正文
    ├─ python-docx 本地生成 .docx
    └─ 飞书发送文件
```

**优势：**
- 直接在飞书交互，体验无缝
- Python 全控制，docx 样式精细
- 可定时、可串联其他工作流

**劣势：**
- 多模态能力依赖当前模型（非专用 VL 模型）
- 知识库检索需自建（kb-retriever 或直接文件读取）
- 每次对话上下文有限，复杂模板可能超出
- 需要编写和维护 SKILL.md

### 路线 C：Dify + Hermes 混合（最佳实践）

**核心架构：**

```
用户 → 飞书 → Hermes Agent
                  ↓
            调用 Dify API（HTTP Request）
                  ↓
            Dify 工作流执行（多模态识别+知识库+生成）
                  ↓
            返回 .docx → Hermes → 飞书发送文件
```

**优势：**
- 飞书交互体验（Hermes 端）
- Dify 多模态+知识库能力（Dify 端）
- 各取所长，松耦合
- .docx 生成放在 Dify Code 节点或 Dify HTTP 调用独立微服务

**劣势：**
- 多一个 HTTP 调用环节
- 依赖 Dify 服务可用性
- 端到端调试链路较长

## 三、推荐方案：路线 A（Dify 工作流优先）

### 理由

1. **多模态是刚需** — 勘察单大量含照片/手写，Dify 内置 VL 模型支持最好
2. **知识库是刚需** — 模板 + 处置方案需要 RAG 检索，Dify 知识库是现成的
3. **你已熟悉 Dify** — 技术栈偏好里 Dify 排第一
4. **可渐进到路线 C** — Dify 工作流先跑通，后续加 Hermes 做飞书入口只是加一个 HTTP 调用的事

### 阶段规划

#### Phase 1：最小可用（MVP）

**目标：** 输入一条勘察文本，输出一份合格 .docx 施工方案

```
输入：文本描述（"XX小区10kV配电室低压柜更换..."）
  → [LLM 节点] 提取关键字段（工程名称、地点、设备型号）
  → [知识库节点] 检索匹配的施工方案模板
  → [LLM 节点] 按模板填充生成报告正文
  → [Code 节点] python-docx 生成 .docx
  → [End 节点] 返回文件
```

**需要准备：**
1. **模板库** — 3-5 份标准施工方案模板（.docx 或 markdown）
2. **处置方案库** — 按场景分类的处置方案文档（含表格）
3. **Dify 知识库** — 上传以上文件，建立数据集
4. **Dify 工作流** — 用 Chatflow 搭建

#### Phase 2：多模态输入

在 Phase 1 基础上，入口增加多模态 LLM 节点：

```
输入：勘察单照片 + 手写备注图片
  → [多模态 LLM 节点] 图片→结构化文本（设备型号、现场条件、注意事项）
  → Phase 1 流程
```

**模型选择：** Qwen2.5-VL-72B（SiliconFlow / 阿里云 API）

#### Phase 3：Hermes 飞书入口（可选）

```
飞书发图片/文件 → Hermes Agent
  → 调用 Dify API → 工作流执行 → 返回 .docx
  → 飞书发送文件给用户
```

## 四、需要你准备的材料

### 4.1 模板文档（必选）

收集 5-10 份历史施工方案报告作为模板，最好是：
- 覆盖不同施工场景（电缆敷设、设备更换、杆塔组立等）
- Word 格式，含完整章节结构
- 标注出哪些部分可以标准化替换

### 4.2 处置方案知识文档（必选）

按施工场景分类的处置方案文档，例如：
- `配电室设备更换施工方案.md`
- `电缆沟开挖及敷设施工方案.md`
- `杆上变压器安装施工方案.md`
- ...

每个文档包含：施工流程、技术要求、安全措施、质量验收标准

### 4.3 标准表格模板（可选）

常用表格格式：
- 施工进度表
- 材料清单表
- 人员配置表
- 验收记录表

## 五、实现步骤（Phase 1）

| 步 | 内容 | 预估时间 |
|----|------|----------|
| 1 | 整理模板文档，上传 Dify 知识库 | 30min |
| 2 | 整理处置方案文档，上传 Dify 知识库 | 30min |
| 3 | Dify Chatflow 搭建：LLM 字段提取节点 | 20min |

| 6 | Dify Code 节点：python-docx 生成 .docx | 1h |
| 7 | 验证：输入测试数据，检查输出格式 | 30min |
| **总计** | | **~3.5h** |

## 六、风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| .docx 格式在 Dify Code 节点超时 | 中 | 分两段生成：先 LLM 出结构化内容，Code 节点只做格式转换 |
| LLM 生成的表格不符合行业规范 | 中 | 固定表格模板，LLM 只填数据不改格式 |
| 模板匹配不准确（输入场景模糊） | 低 | LLM 先做场景分类（电缆/设备/杆塔...），再按分类检索 |
| 勘察照片不清导致识别错误 | 中 | 多模态节点设置信度阈值 <0.7 的字段标记"需人工复核" |
| Dify Code 节点 python-docx 不预装 | 低 | Code 节点可 `pip install python-docx` 或改用预装镜像 |

## 七、下一步

如果你有现成的模板文档和处置方案文档，可以直接开始 Phase 1 步骤 1。

如果你不确定选哪条路线，我可以按以下维度帮你做最终决断：

| 你的情况 | 推荐路线 |
|----------|----------|
| 勘察单主要是文字+表格 | A（Dify）或 B（Hermes）均可 |
| 勘察单大量含现场照片 | **A（Dify 多模态）** |
| 需要通过飞书/企业微信交互 | **C（Dify+Hermes 混合）** |
| 需要定时批量生成 | **B（Hermes Skill + cron）** |
| 最终用户是业务人员而非自己 | **A（Dify 可视化可调）** |
