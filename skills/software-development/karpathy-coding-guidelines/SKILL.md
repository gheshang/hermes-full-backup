# Karpathy 编码元规则

**优先级：高于角色库。** 角色库决定"怎么做好某类任务"，本规则决定"不管做什么任务都别犯蠢"。

**权衡：偏向谨慎而非速度。琐碎任务自行判断，非琐碎工作必须严格遵守。**

## 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

实现前：
- 不确定就问，不猜。明确说明假设。
- 有多种理解时全部呈现，不默默选一个。
- 存在更简单方案时必须提出异议。
- 搞不懂就停，指出哪里困惑，要求澄清。

## 2. 简洁优先

**最少的代码解决问题。不做推测性设计。**

- 不加没要求的功能
- 一次性代码不建抽象
- 不加没要求的"灵活性"或"可配置性"
- 不为不可能发生的场景做错误处理
- 200 行能写 50 行的，重写

**检验标准：** 资深工程师会觉得过于复杂吗？是 → 简化。

## 3. 精准修改

**只碰必须碰的。只清理自己造成的混乱。**

编辑已有代码：
- 不"改进"相邻代码、注释、格式
- 不重构没坏的东西
- 匹配已有风格，即使你更倾向不同写法
- 注意到无关死代码 → 提一下，不删

自己的改动产生孤儿代码时：
- 删因自己改动而变得无用的导入/变量/函数
- 不删预先存在的死代码（除非被要求）

**检验标准：** 每一行修改都必须能直接追溯到用户请求。

## 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

| 错误做法 | 转化为 |
|---------|--------|
| "添加验证" | "为无效输入写测试，然后让它通过" |
| "修复 bug" | "写一个能重现 bug 的测试，然后让它通过" |
| "重构 X" | "确保重构前后测试都通过" |

多步骤任务必须声明计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

强成功标准 → 能独立循环。弱标准（"让它工作"）→ 需要不断澄清。

## 与角色库的关系

| 场景 | 执行顺序 |
|------|---------|
| 写代码 | 本规则（先） → 角色库的领域角色（后） |
| 审代码 | 角色库的代码审查员/安全工程师（先） → 本规则验证每行修改是否追溯用户请求（后） |
| 重构 | 本规则的"精准修改" → 角色库的架构师/高级开发者 |

## 反模式速查

| 原则 | 反模式 | 正确做法 |
|------|--------|---------|
| 编码前思考 | 默默选一种理解然后执行 | 列出所有理解，让用户选 |
| 简洁优先 | 为一次性代码建策略模式/抽象层 | 50 行能搞定就不写 200 行 |
| 精准修改 | 改 bug 时顺手"改进"相邻代码 | 每行改动必须追溯到用户请求 |
| 目标驱动 | "让它工作" | "写测试→让它通过→验证不回归" |

## 反例库

完整反例见仓库 `~/andrej-karpathy-skills/EXAMPLES.md`，覆盖：
- 隐藏假设（export 功能假设了范围/格式/字段）
- 过度抽象（折扣计算搞成策略模式）
- 推测性功能（存偏好加了缓存/校验/通知）
- 顺手重构（改 bug 时加了类型提示和文档字符串）
- 模糊目标（"修复认证"vs"密码修改后旧 session 失效"）
